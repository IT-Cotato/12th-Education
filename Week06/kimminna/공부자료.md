# 0. 왜 인증(Authentication)과 인가(Authorization)가 필요한가?

### HTTP의 특징

- HTTP는 **무상태(stateless)** 프로토콜
- 서버는 이전 요청을 기억하지 못함
- 즉, 요청이 올 때마다
  “이 요청을 보낸 사용자가 누구인지”를 알 수 없음

### 그래서 필요한 것

- 사용자를 **식별**하고
- 로그인 상태와 **권한**을 유지하기 위한 수단

이 역할을 하는 것이 **쿠키, 세션, 토큰**

# 1. 웹사이트 쿠키란?

## 1.1 쿠키란?

- 웹사이트가 **사용자의 브라우저에 저장하는 작은 데이터 조각**
- 텍스트 형태의 key-value 데이터
- 서버 또는 클라이언트(JS)가 생성 가능
  ### 쿠키에 저장되는 정보 예시
  - 세션 식별자
  - 로그인 상태
  - 언어 설정, 테마 설정
  - 사용자 행동 추적 정보

## 1.2 쿠키는 어디에 저장되는가?

- **사용자 로컬 환경 (브라우저)**
- 브라우저별로 전용 저장소 존재
  ### 예시 (Chrome)
  ```
  개발자 도구 → Application → Storage → Cookies
  ```

  - 실제로는 브라우저 고유 디렉토리에 파일 형태로 관리
  - 설정에 따라:
    - 서버에서만 접근 가능
    - JS에서 접근 가능

## 1.3 쿠키의 주요 사용 목적

### (1) 사용자 세션 유지

- 로그인 후 세션 ID를 쿠키로 저장
- 이후 요청마다 쿠키 자동 전송
- 서버는 쿠키를 통해 사용자를 식별

### (2) 개인화

- 언어, 다크모드 등 사용자 설정 저장

### (3) 추적

- 방문 페이지, 체류 시간 기록
- 광고 맞춤화 및 서비스 개선 목적

# 3. 쿠키와 개인정보 보호 이슈

## 3.1 동의 없는 추적

- 사용자 행동 프로파일링
- 광고 네트워크에서 광범위하게 사용

## 3.2 데이터 유출 위험

- 쿠키에 민감 정보 저장 시
- XSS 공격으로 탈취 가능

## 3.3 익명성 감소

- 장기간 사용자 행동 추적

# 4. 세션

### 세션이란?

- **서버 측**에 사용자 상태를 저장하는 방식
- 클라이언트에는 **세션 ID만 쿠키로 저장**

### 특징

- 서버가 사용자 상태를 기억
- 보안성은 높지만
- 서버 확장성에 불리

# 5. 토큰

### 토큰이란?

- 사용자를 인증하는 문자열 데이터
- 서버에 상태를 저장하지 않음
- 클라이언트가 토큰을 보관하고 매 요청마다 전송

# 6. JWT (Json Web Token)

## JWT

### 6.1 JWT란?

- JSON 기반의 토큰 인증 방식
- 클라이언트–서버 간 인증/인가에 사용
- **상태 비저장(stateless) 인증**을 가능하게 함

JWT는 **암호화된 토큰이 아니라 서명된 토큰**

---

### 6.2 JWT 구조

1. **Header**
   - 토큰 타입, 해싱 알고리즘 정보
2. **Payload**
   - 사용자 정보 (userId, role 등)
   - 누구나 디코딩 가능 → 민감 정보 금지
3. **Signature**
   - Header + Payload + Secret Key로 생성
   - 위변조 방지 역할

---

### 6.3 JWT 기반 인증의 특징

- 서버는 사용자 상태를 저장하지 않음
- 매 요청마다 토큰 검증
- 확장성과 모바일/SPA 환경에 유리

## 7. 토큰 저장 위치 비교

### 7.1 메모리 (변수)

- 보안성 👍
- 새로고침 시 소멸 → UX 👎

### 7.2 웹 스토리지

- **세션 스토리지**
  - 탭 단위 유지
  - XSS 취약, CSRF 안전
- **로컬 스토리지**
  - 영구 저장
  - XSS 취약, CSRF 안전

### 7.3 쿠키

- 기본 설정: XSS / CSRF 모두 취약
- 보안 옵션 사용 시 개선 가능

---

### 쿠키 보안 옵션

```
Set-Cookie: token=xxx; HttpOnly; Secure; SameSite=Lax

```

- `HttpOnly`: JS 접근 차단 (XSS 방어)
- `Secure`: HTTPS에서만 전송
- `SameSite`: CSRF 방어

## 8. 안전한 JWT 인증 구조

안전한 JWT 저장을 위해서는 백엔드와 프론트엔드의 협업이 필요하고, 서로 간의 이해가 필수임.

### 권장 방식: Access / Refresh Token 분리

### 인증 흐름

1. 로그인 성공
2. 서버
   - Access Token → 응답 바디
   - Refresh Token → HttpOnly 쿠키
3. 프론트엔드
   - Access Token → 메모리 저장

### API 요청

- Authorization Header에 Access Token 포함

### Access Token 만료

- Refresh API 호출
- 새 Access Token 발급

### Refresh Token 만료

- 재로그인 필요

위와 같이 진행되면 refresh token이 저장된 쿠키는 외부 경로와 js 상에서의 접근이 불가능해짐. (CSRF, XSS 공격에서의 안전성 확보)

access token이 저장된 비공개 변수는 XSS, CSRF 공격을 시도할 방법이 사라지며, 토큰이 휘발되어 사라졌던 UX 문제도 해결됨!
