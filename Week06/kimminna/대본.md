### 1

안녕하세요.

이번 CS 교육 발표를 맡은 **교육팀 김민아**입니다.

이번 CS 교육의 주제는 **쿠키, 세션, 그리고 토큰**입니다.

프로젝트를 시작하면서 가장 먼저 고민하게 되는 부분 중 하나가

**인증과 인가 시스템을 어떻게 구현할 것인가**라고 생각하는데요,

오늘 발표를 통해 각 인증 방식의 특징을 이해하고

프로젝트에 조금이나마 도움이 되셨으면 좋겠습니다.

### 2

이번 교육의 목표는 다음과 같습니다.

첫 번째로 **쿠키, 세션, 토큰의 개념을 이해**하고,

두 번째로 **JWT의 개념과 특징을 이해**하는 것입니다.

그리고 각각의 인증 방식이

**어떤 차이가 있는지**,

**어떤 방식으로 동작하는지** 알아보는 시간을 가져보겠습니다.

### 3.

인증과 인가 시스템은 왜 필요할까요?

기본적으로 **HTTP 프로토콜은 상태를 가지지 않는 프로토콜**입니다.

즉, 서버는 클라이언트가 보낸 **이전 요청을 기억하지 못합니다.**

### 4

서버가 상태를 기억하지 못한다면,

사용자는 로그인을 유지할 수 없고

서버는 사용자별 데이터를 구분할 수 없으며

사용자에 대한 권한 판단도 할 수 없게 됩니다.

이러한 상황에서는

정상적인 서비스 제공이 어렵게 됩니다.

### 5

그래서 우리는 서비스에

**인증과 인가 시스템을 구현해야 하는데요.**

인증/인가 시스템은

사용자를 식별하고

권한을 검증하며

요청 간 상태를 유지하는 데 필수적인 요소입니다.

### 6

이러한 인증, 인가 시스템을 구현하기 위해

등장하는 개념이 바로 **쿠키, 세션, 토큰**입니다.

이 개념들은

HTTP의 **무상태(stateless) 특성을 보완하고**,

상태를 유지하기 위한 수단으로 사용됩니다.

### 7

먼저 **쿠키**에 대해 알아보겠습니다.

쿠키는 웹사이트가

**사용자의 브라우저에 저장하는 작은 데이터**입니다.

키와 값이 한 쌍으로 이루어진 텍스트 형태이며,

서버 또는 클라이언트에서 생성할 수 있습니다.

### 8

다음 사진과 같이

개발자 도구 → Application → Cookies 탭에서

쿠키의 **Name과 Value 값**을 확인할 수 있습니다.

### 9

쿠키의 목적은 무엇일까요?

쿠키는 사용자 세션 유지, 개인화, 추적을 위해서 사용되는데요

### 10

클라이언트는 서버에게 요청할 때마다 쿠키를 담아서 전송합니다.

그리고, 서버는 클라이언트가 보낸 쿠키를 이용해서 사용자를 식별하게 됩니다.

### 11

또한, 쿠키는 개인화를 위한 설정에도 사용됩니다.

예를 들어,

사용자의 언어를 서비스에 등록해 두는 것,

다크모드와 같은 테마를 지정해 두는 등 사용자의 환경을 서비스에 유지하는 데 쓰이기도 합니다.

### 12

쿠키는 사용자를 추적하는 데도 사용됩니다.

사용자가 방문한 페이지, 체류 시간, 클릭 패턴 등을 분석해 사용자에게 맞춤형 광고를 제공하거나
서비스 개선을 위한 데이터로 활용되기도 합니다.

### 13

그렇다면 쿠키를 이용한 인증 방식은 어떻게 동작할까요?

쿠키 기반 인증 방식에서는 **클라이언트가 인증 정보를 관리**하는 특징을 가집니다.

클라이언트가 로그인 요청을 보내면,

서버는 인증 정보를 쿠키에 담아 응답하고,

클라이언트는 이 쿠키를 저장하게 됩니다

### 14

이후 클라이언트는 요청을 보낼 때마다 쿠키를 함께 전송하고,

서버는 쿠키에 담긴 정보를 바탕으로 사용자를 식별하고 인가 처리를 하게 됩니다.

### 15

이 방식은 과연 안전할까요?

쿠키 인증 방식의 문제점은 다음과 같습니다.

클라이언트가 쿠키를 위조할 수 있고, 브라우저가 쿠키를 자동으로 전송하기 때문에

CSRF, XSS 공격에 취약합니다. 또한, 쿠키 데이터 크기에 제한이 있다는 문제도 있는데요.

이러한 이유로 쿠키만으로 인증을 처리하는 방식은 보안상 한계가 존재합니다.

### 16

이러한 쿠키 인증 방식의 문제점을 개선하기 위해

등장한 개념이 바로 **세션**입니다.

세션은 **사용자 상태를 클라이언트가 아닌 서버에 저장**하는 방식입니다.

클라이언트는 세션 ID만 쿠키로 저장하게 됩니다.

즉, 세션은 **쿠키를 기반으로 동작하는 인증 방식**입니다.

### 17

세션 인증 방식은 다음과 같이 동작합니다.

클라이언트가 로그인 요청을 보내면,
서버는 사용자 인증 정보를 서버에 저장하고
세션 ID를 생성해 클라이언트에게 응답합니다.

클라이언트는 이 세션 ID를 쿠키에 저장하게 됩니다.

### 18

이후 클라이언트는

쿠키에 저장된 세션 ID를 이용해 인가 요청을 보내고,

서버는 세션 저장소에 있는 정보를 조회해 인가 처리를 하게 됩니다.

### 19

세션 인증 방식의 문제점은 무엇일까요?

우선, 서버가 사용자 인증 정보를 관리하기 때문에 서버에 메모리 부하가 발생할 수 있습니다.

서버가 여러 대로 확장될 경우는, 세션 공유를 위한 별도의 저장소도 필요하게 됩니다.

또한, 세션은 쿠키를 사용하기 때문에 쿠키 탈취의 위험이 여전히 존재한다는 문제도 있습니다.

### 20

쿠키와 세션 방식의 단점을 개선하기 위해

등장한 개념이 바로 **토큰**입니다.

토큰은 **사용자를 증명하는 문자열 데이터**입니다.

토큰 인증 방식에서는 서버가 상태를 저장하지 않고, 클라이언트가 토큰을 직접 관리하게 됩니다.

### 21

토큰 인증 방식에서는
클라이언트가 로그인 요청을 보내면 서버는 토큰을 발급해 응답합니다.

클라이언트는 이 토큰을 저장하고, 이를 통해 사용자 인증 정보를 관리하게 됩니다.

### 22

이후 클라이언트는

토큰을 요청에 포함시켜 서버에 전송하고, 서버는 토큰을 검증한 뒤 인가 요청을 처리하게 됩니다.

### 23

토큰의 종류에는 JWT 이외에도 여러 토큰이 존재하지만, 여러 토큰 형식 중 JWT 형식이 상태를 저장하지 않는 특징을 가지므로 많이 사용되는데요,

상태를 가지지 않는다는 것은 다시말해 서버에서 토큰을 저장할 필요가 없어지므로, 데이터베이스와 통신할 필요가 없게 되고, 서버 인스턴스가 여러 개 있을 때도 쉽게 확장할 수 있다는 뜻입니다.

JWT는 JSON 형식의 데이터를 안전하게 주고받기 위한 개방형 표준입니다.

### 24

JWT는 헤더, 페이로드, 서명의 세 부분으로 구성됩니다.

### 25

JWT의 상태를 가지지 않는 특징은 JWT의 구조에서 비롯되는데요.

헤더에는 토큰의 유형, 서명 알고리즘을 포함합니다.

페이로드에는 사용자 정보, 사용자 ID, 권한, 만료 시간 등이 포함됩니다.

이 페이로드 부분 덕분에 서버가 별도의 데이터베이스 조회 없이도 사용자의 정보를 확인할 수 있어서 서버의 부하가 줄어들게 됩니다.

서명 부분은 헤더와 페이로드를 조합한 후, 헤더의 서명 알고리즘과 비밀 키를 이용하여 생성되는 부분입니다. 이 서명을 통해 클라이언트가 토큰을 변조하지 않았음을 검증할 수 있고, 신뢰할 수 있는 토큰임을 보장하게 됩니다.

최종적으로 이 세 부분이 인코딩 된 후 하나의 문자열로 결합되어 JWT 토큰을 구성하게 됩니다.

이렇게 구성된 토큰은 필요한 모든 정보와, 변조 감지를 위한 서명 부분을 토큰에 자체적으로 포함하고 있으므로, 서버는 별도의 세션 저장소를 유지할 필요 없이, 단순히 클라이언트가 JWT를 가지고 있으면 서버는 이 토큰을 검증하여 사용자의 인증 상태를 확인할 수 있게 됩니다.

### 26

JWT를 이용한 인증 방식은 다음과 같이 이루어집니다.

클라이언트가 로그인을 요청하면,

서버는 액세스 토큰과 리프레쉬 토큰을 발급하여 응답합니다.

클라이언트는 이 토큰들을 브라우저의 별도의 공간에 저장하게 됩니다.

### 27

클라이언트는
액세스 토큰을 이용해 인가 요청을 보내고,
서버는 토큰이 유효하다면 요청을 처리합니다.

만약 액세스 토큰이 만료되었을 경우,
클라이언트는 리프레시 토큰을 이용해서
토큰 재발급을 요청하게 됩니다

그렇다면 JWT 인증 방식에서는

**로그아웃은 어떻게 구현해야 할까요?**

JWT 인증 방식에서는 서버가 사용자 인증 상태를 저장하지 않는 **stateless(무상태) 구조**이기 때문에,

로그아웃 시 **클라이언트에 저장된 토큰을 제거하는 방식으로 로그아웃을 구현합니다.** 즉, 클라이언트에 저장된 **액세스 토큰과 리프레시 토큰을 삭제**함으로써

이후 요청에서는 더 이상 토큰이 서버로 전달되지 않게 되고,

그 결과 서버는

해당 사용자를 **인증되지 않은 사용자로 인식**하게 됩니다.

이와 같은 방식이 JWT 인증 방식을 사용할 때 일반적으로 로그인과 로그아웃을 구현하는 흐름입니다.

### 28

지금까지
쿠키, 세션, 토큰 인증 방식에 대해 알아보았습니다.

어떤 인증 방식이 무조건 좋은 것은 아니며, 서비스의 특성에 따라 보안성과 편의성의 균형을 고려해 적절한 방식을 선택해야 합니다.

이번 CS 교육에서 다루지는 않았지만, 프론트엔드 개발자분들께서는 서버로부터 받은 인증 정보를 웹 스토리지, 메모리, 쿠키 중 과연 어디에 저장하는 것이 안전할지 한 번 더 고민해 보시면 좋겠습니다.

이상으로 발표를 마치겠습니다.
