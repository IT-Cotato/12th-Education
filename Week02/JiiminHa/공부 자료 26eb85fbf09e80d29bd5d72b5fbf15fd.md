## **폭포수(Waterfall) vs 애자일(Agile) — 정의 및 특성 비교**

| **항목** | **내용** |
| --- | --- |
| **Waterfall 모델 정의** | 순차적(Linear), 단계별(Phase-based)로 진행됨. Requirements → Design → Implementation → Testing → Deployment → Maintenance 순으로 각 단계가 완료된 후 다음으로 넘어감. |
| **Waterfall의 강점** | 요구사항이 명확하고 변화가 적을 때 예측 가능성 높음. 문서화 중심이고, 큰 프로젝트 / 규제/안전이 중요한 시스템 등에 적합. 초기 설계 단계에서 전체 구조가 정해지므로 이후 변경 비용이 큼. |
| **Waterfall의 약점** | 변경 대응이 어렵고, 고객 피드백이 늦게 발생. 전체 시스템이 완성되기 전까지 작동 가능한 부분을 보여주기 힘듦. 높은 위험성(예: 요구사항이 잘못되었을 경우)과 재작업 비용. |

| **항목** | **내용** |
| --- | --- |
| **애자일(Agile) 정의** | 변화를 수용하고 반복적(Iterative), 증분적(Incremental)으로 개발함. 작은 단위로 기능을 개발 → 검토 및 사용자/고객 피드백 반영 → 개선하는 주기를 가짐. 애자일 선언문(Agile Manifesto)의 가치와 원칙들 중심. |
| **애자일의 가치(Value) 네 가지** | * 개인과 상호작용(Individuals and interactions) > 프로세스와 도구(Processes and tools) * 작동하는 소프트웨어(Working software) > 포괄적인 문서(Comprehensive documentation) * 고객과의 협업(Customer collaboration) > 계약 협상(Contract negotiation) * 변화에 대응(Responding to change) > 계획을 따르는 것(Following plan) |
| **애자일의 특성** | 짧은 반복 주기(iteration 또는 sprint, 보통 1~4주) Cross-functional 팀, 자율성과 협업 강조 지속적인 통합(CI), 지속적인 테스트, 피드백 중심 최소한의 문서화, 우선순위 조정 가능성 높음. |
| **애자일의 장점 / 단점** | **장점**: 시장/고객 요구 변화에 민첩하게 대응, 실패비용 낮춤, 초기 작동 버전(프로토타입 또는 최소 기능 제품, MVP)을 통해 검증 가능. **단점**: 요구사항이 자주 바뀌면 스코프 헬(의도치 않은 기능 증대)이 생길 수 있고, 문서나 명확한 설계가 부족하면 시스템 규모가 커질 때 유지보수가 어려움. |

## **비유: “3층집 짓기” 관점에서 비교**

| **방식** | **비유적 설명** | **장단점 (3층집 비유 기준)** |
| --- | --- | --- |
| **Waterfall** | 처음부터 1층, 2층, 3층을 한꺼번에 설계하고 각 층을 동시에 혹은 명확한 설계 후 완공하는 조립식 방식 | **장점**: 전체 집 구조가 미리 정해져 있어 인테리어, 전기/배관 등 설계 충돌이 적고, 예산/시간 계획을 세우기 쉬움.  **단점**: 1층에서 고객 반응이 좋지 않으면 2~3층 완공 후에 큰 문제 발견됨; 변경이 어렵고 비용이 많이 듦. |
| **Agile** | 먼저 핵심 이유(왜 집을 짓는가)를 탐색하고, 1층짜리 펜션을 먼저 짓는 MVP 형태로 시작 → 시장 반응/수익/사용자 피드백 본 다음 2층 확장 여부 결정 | **장점**: 실패 위험 낮고, 자원(시간/비용) 낭비 감소; 고객/사용자 피드백 중시; 변화에 유연함.  **단점**: 처음부터 전체 구조가 완전하지 않으면 나중에 확장할 때 구조적 제약이 있을 수 있음; 초기 버전이 빈약해 보일 수 있음; 전체 설계 및 인프라 고려가 부족하면 리워크가 생길 수 있음. |

## **개발자 입장에서의 애자일**

| **장점** | **설명** | **출처** |
| --- | --- | --- |
| **자기주도성(Self-ownership) + 책임감 증대** | 스프린트 동안 개발 항목을 팀이 같이 선정하고 책임지니까, “왜 내가 이걸 만드는지 / 이 기능이 어떤 가치가 있는지” 알 수 있고 주인의식이 생김. | BuiltIn: “11 Benefits of Agile Methodology” 중 “Increased employee input” |
| **지속적인 피드백 + 빠른 개선** | 코드가 돌아가는 기능 단위로 자주 리뷰되고 피드백이 오니까, 버그나 구조적 문제 빨리 발견 가능함. 덕분에 리팩토링도 자주 가능하고 기술 부채가 누적되는 속도가 늦춰짐. | Wrike: 품질 향상, 고객 만족도가 빨라지는 항목  ; 또한 “Benefits of Agile Development …” |
| **변화에 유연하게 대응 가능** | 요구사항이 바뀌거나 우선순위가 바뀔 때, 폭포수처럼 전체 계획이 다 바뀌는 것이 아니라 일부 스프린트 안에서 조정 가능함. | Wrike & Planview Agile Benefits 문서 |
| **단기 목표 설정 + 진척 시각화가 잘 됨** | 매 스프린트마다 무엇을 만들지, 어느 정도 했는지 명확 → 동료들과도 “진행 중인 것 / 남은 것”이 눈에 보이니까 부담/불확실성이 줄어듦. | Planview: 작업 효율과 제품 품질 등 항목 |
| **팀 협업 / 커뮤니케이션 증대** | 개발자, QA, 디자인, 기획 간 끊임없이 대화함. 매일 스탠드업, 리뷰, 회고 등이 있어서 고립감 줄고 정보 공유가 잘 됨. | BuiltIn: cross-functional collaboration 등  ; What is Agile Design (IxDF) 중 디자인/팀 가시성 부분 |

| **주의할 점 / 단점** | **설명** |
| --- | --- |
| **스코프 관리 어려움** | 자주 변경이나 추가 요청이 오면 스프린트 내 또는 전체 프로젝트 범위가 너무 커질 수 있음. 우선순위가 자주 바뀌면 집중이 흐트러질 수 있음. |
| **기술 부채/인프라 고려 부족 가능성** | 빠르게 기능 중심으로 움직이면서 테스트나 리팩토링, 아키텍처 문제 등을 뒤로 미루면 나중에 유지보수나 확장 시 큰 비용이 들 수 있음. |
| **초기 예측성 낮음** | 얼마나 걸릴지, 전체 시스템이 어떻게 될지, 전체 구조가 어떤 식일지에 대한 예측이 어려움. 예산/일정 고정되어 있는 프로젝트라면 부담됨. |
| **과한 반복/회의 부담** | 매일 미팅, 스프린트 계획, 리뷰, 회고 등이 반복되기 때문에 회의 준비/정리/참여 부담이 커질 수 있음. 특히 문서나 사전 설계가 부족하면 의사결정 지연이 생길 수 있음. |

## **기획자 / 디자이너 입장에서의 애자일**

| **장점** | **설명** |
| --- | --- |
| **초기 사용자/고객 피드백 반영 가능** | 디자인 초안이나 프로토타입을 빨리 만들고 실제 사용자 또는 이해관계자의 의견을 받아서 수정 가능 → 출시 전 실패 위험 줄음. |
| **디자인 방향 지속성 확보 + 설계 일관성 유지** | 디자인이 초기에만 정해지고 개발 도중 끊기는 게 아니라 전체 과정(sprint) 동안 디자이너가 계속 참여 → 디자인이 개발에 맞춰 조정되며 서로 상충되는 요소(개발 제약 등) 미리 파악 가능. |
| **우선순위 조정 가능성 및 리소스 낭비 감소** | 중요도가 낮은 기능/디자인 요소는 미룰 수 있고, 중요한 UX/UI 요소가 먼저 반영됨. 너무 많은 시간 소비될 기능을 늦추거나 제거 가능. |
| **팀 간 협업 및 이해 증진** | 기획/디자인/개발이 자주 만나고 상호 이해 높아져서 디자인 의도, 제약사항 등이 잘 공유됨. 버그라기보단 인터랙션/디자인 문제를 빨리 해결 가능. |

| **주의할 점 / 단점** | **설명** |
| --- | --- |
| **디자인 완성도 초기에 낮을 수 있음** | 초기 스프린트에서는 가벼운 프로토타입 또는 최소 기능 중심 디자인이므로 최종 모습보다 덜 다듬어진 느낌이 들 수 있음. 사용자에게 인상 안 좋을 위험이 있음. |
| **디자인 변경·재작업 빈도 증가** | 사용자 피드백, 개발 제약, 우선순위 변경 등에 의해 디자인 작업물이 반복해서 바뀔 수 있고, 이로 인한 작업 부담이 커질 수 있음. |
| **문서화 및 전달 명확성 부족** | 문서/디자인 시스템이 잘 정리되지 않으면, 디자인 의도나 세부 사양이 개발 쪽에서 오해되거나 누락될 가능성 있음. 특히 디자이너가 여러 명이거나 프로젝트 규모가 클 때 더 중요함. |
| **리소스 및 시간 관리 어려움** | 디자인적으로 많은 아이디어 탐색이나 사용자 리서치가 필요할 경우, 짧은 스프린트 내에 모두 하려면 타이트함. 또는 스프린트에 맞추지 못하면 다음 스프린트로 미루어져 병목 생길 수 있음. |

## **애자일 vs 데브옵스(DevOps) 비교 및 역할**

| **항목** | **Agile** | **DevOps** |
| --- | --- | --- |
| **핵심 정의 / 목적** | 반복/증분 개발(Iterations/Increments), 변화 대응, 고객 중심 가치를 빠르게 제공하는 것. | 개발(Dev)과 운영(Ops)의 경계 허물기, 자동화/플랫폼 설계 및 반복적, 안정적인 서비스 전달 등 전체 소프트웨어 개발→배포→운영 주기의 효율성과 품질 향상. |
| **중점 활동 / 프로세스** | 스프린트 계획, 데일리 스크럼, 백로그 우선순위 설정, 리뷰/회고. 반복되는 피드백 루프. | CI/CD (Continuous Integration / Continuous Delivery), 자동화된 테스트 & 배포, 운영 모니터링/피드백, 지속적인 개선, 인프라 자동화, 시스템 안정성 확보. |
| **팀과 책임 범위** | 제품 기능 중심, 기획/디자인/개발 간 협업, 보통 작은 크로스펑셔널 팀. 변화 및 사용자 요구 반영이 중요. | 개발팀 + 운영팀 + 품질보증(Test) + 보안 등의 역할 간 경계를 줄이는 통합적 책임. 전체 서비스 라이프사이클(배포 이후 운영 포함) 책임 공유. |
| **측정/피드백 주기** | 비교적 짧은 주기 (1~4주 스프린트)로 피드백, 사용 가능한 소프트웨어 산출. | 배포 빈도(Deployment Frequency), 변화의 준비성(Lead Time for Changes), 실패율(Change Failure Rate), 복구 시간(Time to Recover) 등의 지표 활용. 안정성과 속도의 균형을 맞춤. |

### **데브옵스(DevOps)란 무엇인가?**

**1. 정의: 문화 철학, 방식, 도구의 조합**

- DevOps는 애플리케이션과 서비스를 빠른 속도로 제공할 수 있도록 조직의 역량을 향상시키는 문화 철학, 방식, 도구의 조합입니다.
- 기존에 분리되어 있던 개발(Development)팀과 운영(Operations)팀이 더 이상 "사일로"에 묶여 있지 않고 긴밀하게 협력하는 문화를 의미합니다.

**2. 목표: 속도와 안정성을 통한 비즈니스 가치 창출**

- **속도:** 고객을 위해 더 빠르게 혁신하고, 시장 변화에 더 잘 적응하여 효율적으로 비즈니스 성과를 창출합니다.
- **신속한 제공:** 릴리스의 빈도와 속도를 개선하여 제품을 더 빠르게 혁신하고 개선합니다.
- **안정성:** 애플리케이션 업데이트와 인프라 변경의 품질을 보장하여, 최종 사용자에게 지속적으로 긍정적인 경험을 안정적으로 제공합니다.

**3. 주요 실천 방식 (Key Practices)**

- **지속적 통합 및 지속적 전달 (CI/CD):**
    - 코드 변경 사항을 중앙 리포지토리에 정기적으로 병합하고(지속적 통합), 프로덕션에 릴리스하기 위한 코드 변경을 자동으로 빌드, 테스트 및 준비하는(지속적 전달) 방식입니다.
    - 소프트웨어 릴리스 프로세스를 자동화하여 혁신 속도를 높입니다.
- **코드형 인프라 (Infrastructure as Code):**
    - 코드를 사용하여 인프라를 프로비저닝하고 관리하는 방식입니다.
    - 수동으로 리소스를 설정할 필요 없이, 반복 가능하고 효율적인 방식으로 개발, 테스트, 프로덕션 환경을 관리할 수 있습니다.
- **모니터링 및 로깅 (Monitoring & Logging):**
    - 지표와 로그를 모니터링하여 애플리케이션 및 인프라 성능이 최종 사용자 경험에 어떤 영향을 미치는지 확인합니다.
    - 실시간 성능에 대한 정보를 얻고 문제에 신속하게 대응할 수 있도록 돕습니다
