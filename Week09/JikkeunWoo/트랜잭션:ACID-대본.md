`#5`트랜잭션 : 더 이상 나눌 수 없는 최소 단위

방금 말씀드린 ‘출금’과 ‘입금’ 과정을 별개의 작업이 아니라, **‘이체’라는 하나의 작업 덩어리**로 묶는 것입니다. 주는 행위와 받는 행위를 합쳐, 하나의 트랜잭션으로 구성한다고도 할 수 있죠.
이 덩어리는 쪼개질 수 없기 때문에, 성공하려면 둘 다 성공해야 하고, 하나라도 실패하면 아예 시작 안 한 것처럼 돌아가야 합니다. 이것을 **All or Nothing**이라고 합니다.

`#7`Commit과 Rollback

이 트랜잭션을 제어하는 명령어가 바로 **Commit**과 **Rollback**입니다.
**Commit**은 모든 작업이 문제없이 성공했을 때, "이 결과를 DB에 진짜로 반영해 줘!" 하고 도장을 찍는 것입니다.
반대로 **Rollback**은 작업 중 하나라도 문제가 생겼을 때, "이건 무효야, 처음으로 돌려놔!" 하고 트랜잭션 시작 전 상태로 되감기 하는 것입니다.
이 두 가지를 통해 우리는 데이터의 안전을 보장받을 수 있습니다.

방금 설명해 드린 원리가 실제 코드로는 어떻게 구현되는지 살펴보겠습니다

---

`#8`Commit과 Rollback 코드 예시

```python
try:
start_transaction()
# 출금
account_a.balance -= 5000
# 입금
account_b.balance += 5000
commit()
except Exception:
rollback()
```

**All or Nothing 원칙을 코드로 간단하게 구현한 예시인데요,**

**(코드의 `try` 부분을 가리키며)**

먼저 `try` 문 안에서 트랜잭션을 시작합니다. 보시는 것처럼 **'a에게 출금, 마이너스 오천원'**과 **'b에게 입금, 플러스 오천원'**이라는 두 개의 명령이 하나의 묶음으로 들어가 있죠. 만약 이 과정이 모두 순조롭게 끝난다면, 마지막에 있는 **`commit()`** 명령어를 만나게 됩니다. 여기서 **확정** 을 마치고, 변경 사항을 데이터베이스에 영구적으로 기록하는 거죠.

**(코드의 `except` 부분을 가리키며)**

만약 입금 과정에서 네트워크 오류가 나거나 시스템이 멈추면 어떻게 될까요? 이때 프로그램은 `except`, 즉 예외 상황으로 빠지게 됩니다. 여기서 바로 **`rollback()`** 명령을 실행합니다.

이 `rollback()`이 실행되는 순간, 앞에 있었던 출금 기록은 없던 일이 되고 데이터는 트랜잭션 **시작 전의 안전한 상태로 되감기** 됩니다. 이렇게 `commit`과 `rollback`이라는 두 장치를 통해, 우리는 어떤 상황에서도 돈이 증발하지 않는 안전한 시스템을 만들 수 있습니다.

`#10`Atomicity (원자성)

첫 번째는 **Atomicity, 원자성**입니다.
원자는 물질을 이루는 최소 단위라 더 이상 쪼개질 수 없다고 배우셨죠? 트랜잭션도 마찬가지입니다.
트랜잭션 안의 작업들은 마치 하나의 원자처럼 동작해야 합니다.
아까 계좌 이체 예시와, 좌측 이미지의 write 4개 작업을 묶어둔 것 처럼, **"전부 함께 실행되거나, 아니면 아예 실행되지 않거나"** 둘 중 하나여야 한다는 것입니다. ‘어중간하게 실행되는 일은 없어야 한다’ 는 게 원자성입니다.

---

`#11`Consistency (일관성)

두 번째는 **Consistency, 일관성**입니다.
트랜잭션이 완료된 후에도 데이터베이스는 일관된 상태, 즉 **정해진 규칙을 위반하지 않는 상태**여야 한다는 것입니다.

이미지를 보면, 규칙을 지킨 상태 A 에서,규칙을 지킨 상태 B 로만 전환이 가능하고, 규칙 위반이 불가합니다. 
예를 들면, 은행 시스템에 '잔액은 0원 미만이 될 수 없다'라는 규칙(제약 조건)이 있다고 해보겠습니다.
그런데 트랜잭션이 끝났는데 잔액이 마이너스가 되어 있다면? 이건 일관성이 깨진 것입니다.

트랜잭션은 이런 데이터베이스의 규칙을  **시작 전에도, 끝난 후에도** 항상 제약조건을 만족해야 합니다.

---

`#12`Isolation (격리성/고립성)

세 번째는 **Isolation, 격리성** 또는 고립성입니다.
이건 여러 트랜잭션이 동시에 실행될 때 서로에게 영향을 주면 안 된다는 것입니다.

이미지처럼 트랜잭션 A, B 가 동시에 실행되더라도 서로 간섭이 없어야 합니다.
예를 들어, 제가 통장의 잔액을 조회하는 동안, 동시에 친구가 제 통장으로 돈을 보내고 있다고 해봅시다.
친구가 돈을 보내는 트랜잭션이 아직 끝나지도 않았는데(Commit 전인데), 제가 그 변경 중인 임시 잔액을 조회해버리면 엉뚱한 결과가 나오겠죠?
그래서 각 트랜잭션은 마치 혼자 실행되는 것처럼 철저히 격리되어야 합니다. 

그렇다면 여기서, 데이터베이스는 이 격리성을 어떻게 구현할까요?

---

`#13`격리성 - Lock

(방금 격리성에 대해 설명해 드렸는데요. )사실 말은 쉽지만, 실제로는 격리 수준이 여러 단계(READ COMMITTED, REPEATABLE READ 등)라 100% 완전 고립은 성능과 트레이드오프, 즉 **하나를 얻으려면 다른 하나는 어느 정도 포기해야 하는** 관계에 있기도 합니다. 또, 실제 환경에서는 이 격리성을 지키기가 참 어렵습니다.

예를 들어,  **이미지처럼** 두 개의 **트랜잭션 T1과 T2**가 동시에 실행되는 상황을 가정해 보겠습니다. 트랜잭션 T1이 데이터 A를 수정했지만 **아직 커밋(확정)을 하지 않은 상태**에서, 트랜잭션 T2가 들어와 T1의 **미확정 데이터를 읽어버립니다**. 이를 **‘Dirty Read (더티 리드)’**라고 합니다.

만약 T1에서 **`Failure`(실패)가 발생하고 `Rollback`(롤백) 처리**가 되면 어떻게 될까요? 파란색 **화살표**처럼 T1의 변경사항은 모두 취소되고, 데이터 A는 **T1 시작 전의 원래 상태**로 되돌아갑니다.

문제는 T2가 이미 유효하지 않은 데이터를 기반으로 작업을 진행했다는 것입니다. 이는 결국 **트랜잭션 간의 격리성(Isolation)을 위반**하고, 데이터베이스에 심각한 **데이터 일관성(Consistency) 문제**를 발생시킵니다.

이런 문제를 해결하기 위해 데이터베이스는 **락(Lock)**, 즉 '자물쇠'라는 개념을 제공합니다.
화장실을 사용할 때 문을 잠그면 다른 사람이 못 들어오는 것과 똑같은 원리인데요. DB 락은 크게 **데이터를 변경할 때**와 **조회할 때**로 나누어 볼 수 있습니다.

`#14`DB 락 ( 변경 ) - 획득

먼저, 데이터를 변경(Update/Delete)할 때의 락입니다.
상황을 가정해 보겠습니다. 여기서 세션 1은 데이터를 수정하려는 **첫 번째 사용자**를 의미합니다.
세션 1이 트랜잭션을 시작합니다. 이때, 세션 1은 변경을 원하고자 하는 행의 락(Lock)을 먼저 획득합니다. 그 후 해당하는 행에, update 500 이라는 작업(sql)을 수행합니다.

`#15`DB 락 ( 변경 ) - 대기

이때 세션 2가 등장해서 똑같은 데이터를 수정하려고 합니다. 하지만 락은 이미 세션 1이 가지고 있죠? 세션 2는 락이 없기 때문에 작업을 진행하지 못하고 **대기 상태**에 빠집니다.

언제까지 기다릴까요? 세션 1이 `Commit`을 해서 트랜잭션을 종료하고 락을 반납할 때까지입니다. 락이 반납되면 그제야 세션 2가 락을 얻고 수정 작업을 진행할 수 있게 됩니다.

---

`#16`락 타임아웃

그런데 만약 세션 1이 락을 잡은 채 퇴근해버리면 어떻게 될까요? 세션 2는 밤새도록 기다려야 할까요?
다행히 그렇지는 않습니다. **무한정 대기하는 것은 시스템에 치명적**이기 때문에, 우리는 락 타임아웃(Lock Timeout)을 설정할 수 있습니다. 특정 시간 만큼 기다린 후, timeout 에러를 발생시키는 것입니다. 우측의 코드 예시를 보겠습니다.

```sql
# SET LOCK_TIMEOUT <milliseconds>
SET LOCK_TIMEOUT 60000; # 60 초
```

보시는 바와 같이 설정한 시간. 여기선 60초가 지나면, 기다리던 세션 2에서는 타임아웃 오류가 발생하게 하여 하염없는 기다림을 방지할 수 있습니다. 타임아웃이 되면, 대기 중이던 트랜잭션은 보통 예외를 던지고 롤백됩니다.

`#19`**DB 락 (조회)**

마지막으로 조회(Select)할 때의 락입니다.
보통 우리가 `Select` 쿼리로 데이터를 조회할 때는 락을 사용하지 않습니다. 세션 1이 수정 중이어도 세션 2는 조회가 가능한 것이 일반적이죠.

하지만, **"내가 조회하는 동안만큼은 절대 데이터가 변하면 안 돼!"** 하는 중요한 상황이 있습니다.
예를 들어, '기획 감자'의 잔액을 조회한 뒤 복잡한 이자 계산을 수행해야 한다고 칩시다. 계산하는 도중에 누가 잔액을 바꿔버리면 계산 결과가 틀려지겠죠?

이럴 때 사용하는 것이 바로 `select for update` 구문입니다. 아래 코드를 보시면,

```sql
set autocommit false;
select * from member where member_id='memberA' for update; -- 락 획득!
```

이렇게 조회 시점에 강제로 락을 거는 경우, 내가 커밋할 때까지 다른 그 누구도 이 데이터를 건드릴 수 없게 됩니다. 데이터의 정합성이 매우 중요한 금전적인 로직에서 주로 사용되는 강력한 기능입니다.

`#20`Durability (지속성)

마지막 네 번째는 **Durability, 지속성**입니다.
이것은 성공적으로 커밋된 트랜잭션은 **영원히 반영되어야 한다**는 성질입니다.
은행에서 "이체 완료되었습니다"라는 메시지를 봤는데, 갑자기 은행 서버 전원이 꺼졌다고 해서 내 돈이 사라지면 안 되겠죠?
시스템에 장애가 생기더라도, 한 번 커밋된 데이터는 여러곳에 안전하게 저장되어 있어야 한다는 것이 지속성입니다.

`#21`요약 및 마무리

오늘 내용을 요약해 보겠습니다.

**트랜잭션**은 쪼개질 수 없고, DB 의 상태를 변화시키는 논리적인 작업의 단위이고, 성공하면 **Commit**, 실패하면 **Rollback**을 합니다.

그리고 안전한 트랜잭션을 위한  4가지 속성 애시드. **All or Nothing, 원자성(Atomicity)**, **규칙을 지키는 일관성(Consistency)**, **서로 간섭하지 않는 격리성(Isolation)**, **영구적으로 저장되는 지속성(Durability)** 에 대해 알아봤구요.

이 중 격리성(Isolation)을 지키기 위해, 데이터베이스는 **Lock(자물쇠)** 기능을 사용합니다. 변경할 때 뿐만 아니라, 조회 시점에도 `select for update`로 락을 걸어 데이터의 무결성을 지킨다는 사실까지 꼭 기억해 주시기 바랍니다.

이상으로 트랜잭션과 ACID, 그리고 DB Lock에 대한 발표를 마치겠습니다. 감사합니다.
