### 16

프로그래머들은 아주 간단한 데이터베이스를 사용해서 파일의 변경 정보를 관리하는 로컬 VCS를 만들었어요.

하지만 이 방법으로는 다른 개발자와 함께 작업하기 어려웠습니다.

### 17

이 문제를 해결하기 위해서 CVCS(중앙집중식 VCS)가 개발됐는데요. 

파일을 관리하는 서버가 별도로 있고, 클라이언트가 중앙 서버에서 파일을 받아 사용하는 방식이에요.

하지만 CVCS 환경은 몇 가지 치명적인 결점이 있습니다. 

가장 대표적인 것이 중앙 서버에 문제가 발생하는건데요.

### 18

서버가 다운된 동안 아무도 다른 사람과 협업할 수 없고 사람들은 작업물을 백업할 수도 없죠.

무엇보다 중앙 DB에 문제가 생기면 모든 히스토리를 잃는 문제가 있습니다.

그리고 이런 문제점들을 개선한 것이 바로 DVCS이에요.

### 19

git은 저장소와 히스토리를 전부 복제해서 클라이언트로 가져옵니다. 

따라서 서버에 문제가 생겨도 이 복제물로 다시 작업이 가능하게 돼요.

git init과 git clone에 대해 설명 드려볼거에요. 

### 23

먼저 git init인데요,

지금은 이렇게 비어있는 폴더를 코드 편집기에서 열고

### 24

git init을 입력하면 .git 폴더가 생성됩니다.

평범한 폴더가 버전 관리가 가능한 폴더로 변경된거에요.

즉, 버전 관리를 git에게 맡기고 싶을 때 사용하는 명령어가 git init입니다.

### 25

두 번째로 git clone입니다.

깃허브 레포의 web url을 복사해서 git clone과 함께 입력해줍니다.

### 26

test라는 폴더 내부에 레포 이름과 동일한 이름의 폴더가 하나 생겼죠?

원격 저장소의 코드를 git이 그대로 복사해왔기 때문이에요.

### 27

해당 폴더 내부에서는 git init 명령어를 실행했을 때 보았던 .git 폴더가 있음을 확인할 수 있습니다.

### 28

그래서 git init과  git clone이 어떻게 다른가보면요,

상위 수준에서는 둘 다 ‘새 git 레포지토리 초기화’에 사용할 수 있습니다.

하지만 git clone은 git init에 종속되는데요,

즉, git clone은 기존 레포지토리의 복사본을 만들기 위해서, 내부적으로 git init을 먼저 호출합니다.

### 29

이제 본격적으로 깃의 구조에 대해 보려고해요.

- working directory - 현재 작업중인 파일들이 있는 디렉토리
- staging area - 변경된 파일들 중 git이 추적하길 원하는 파일들을 일시적으로 저장하는 곳 (커밋 전)
- repository - 저장소 : 실제로 git이 관리하는 데이터가 저장되는 곳 (커밋 후)
- remote - 원격 저장소 : 인터넷 연결이 필요한 서버 저장소

### 30

이제 이 구조를 조금 키워서 볼게요.

local은 노트북, 데스크탑 같은 환경이고,

remote는 github처럼 사람들과 공유 가능한 환경의 원격 저장소입니다.

### 36

이제 프로젝트를 진행하면서 하나의 레포를 가지고 협업을 하게 될텐데, 팀원이 작업 완료하기까지 기다렸다가 이어서 작업할 수 없잖아요!

그래서 여러 작업을 동시에 진행할 수 있도록 브랜치를 만들어서 작업하게 될 텐데, 

그 동안 가장 많이 사용하게 될 명령어 입니다.

git branch 다음에 브랜치 명을 작성해서 브랜치를 생성하고,

d 옵션을 추가해서 해당 브랜치를 삭제합니다.

어떤 브랜치가 있는지 다 기억할 수 없으니, 브랜치 리스트를 확인하는 명령어인  git branch를 입력해서 확인해볼 수 있어요.
